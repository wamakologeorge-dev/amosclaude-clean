4. Current Repository AI Capabilities

When included in the Customer's plan and correctly configured, the Repository AI
may perform some or all of the following actions within an Authorized Repository:

- respond to supported help, status, inspect, verify, review, plan, explain, and
  fix requests, including supported natural-language requests;
- inspect repository files, pull requests, issues, diffs, workflow results, and
  other evidence available through the Customer's granted permissions;
- identify code-health, test, build, configuration, dependency, and integration
  problems;
- run selected compilation, lint, test, typecheck, build, or verification
  commands in a bounded isolated runner when that runner is available;
- prepare complete-file proposals, patches, regression tests, reports, and
  review comments;
- apply an explicitly authorized and policy-compliant repair to a working branch;
- create commits and draft pull requests after required verification succeeds;
- use failed compiler, test, build, or GitHub Actions evidence to attempt a
  corrected repair on the same pull-request branch;
- repeat a same-pull-request correction cycle within a bounded attempt limit and
  stop with a truthful blocker when the limit or a human-only requirement is
  reached;
- update a GitHub-native execution card showing current stages, tests, changed
  files, branch, commit, delivery state, and exact evidence;
- operate a disabled-by-default Daily Autonomous Builder that selects only
  allowlisted backlog work, enforces repository and path policy, verifies the
  result, and may create only a draft pull request;
- provide read-only project report cards and deterministic repository
  architecture maps where those features are enabled;
- support a governed developer workspace, terminal, model station, Template
  Studio, or related service only when the required separate runtime and
  configuration are deployed.

The capabilities listed above describe possible product behavior, not a promise
that every capability is available in every plan or deployment. They are not a
service-level commitment unless an Order Form expressly says otherwise.

5. Repository AI Safety and Authorization Boundaries

The Commercial Service does not create permissions the Customer has not granted.
All repository actions remain limited by GitHub permissions, branch protection,
required checks, protected-path policy, organization policy, plan entitlements,
human approvals, available credentials, and the configured execution runtime.

The standard Repository AI is designed to keep repository-changing work on a
reviewable branch and to avoid claiming success while required verification is
failing. The Customer is not authorized to use the Commercial Service to bypass
or weaken authentication, authorization, required checks, branch protection,
security review, protected paths, audit controls, or approval requirements.

Unless a separately purchased and explicitly configured product permits the
action, the Repository AI must not be relied upon to:

- automatically merge pull requests;
- push directly to a protected default branch;
- delete repositories;
- change GitHub organization ownership or security settings;
- disclose, recover, or print secret values, private keys, or access tokens;
- deploy to production;
- perform destructive database operations;
- rotate credentials or security keys;
- modify protected workflow, infrastructure, authentication, billing,
  deployment, or security files without the required separate approval; or
- continue indefinitely after a bounded repair limit is reached.

The Commercial Service may refuse, block, defer, or require additional approval
for any action that is sensitive, destructive, ambiguous, outside the allowed
workspace, outside the file limit, unsupported by current evidence, or missing
required credentials or infrastructure.
